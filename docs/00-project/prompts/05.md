# 05 — Admin Panel: Menu, Orders/POS, Inventory, Kitchen Display

## Goal
Build the Admin Panel's core operational surfaces — this is what the old "Tenant Panel" collapsed into.

## Blueprint Reference
§1 (Admin Panel), §4.1–§4.2 (Application Structure), §6 (POS Workflow), §7 (Inventory/Payments/Resilience), §9 step 5.

## Scope
- **Menu management** — `Pages/Admin/Menu/Index.tsx` (`admin` only) with shadcn dialogs/forms for Category, MenuItem, Modifier CRUD.
- **Orders/POS** — `Pages/Admin/Orders/Index.tsx` and `Pages/Admin/Pos/Index.tsx` (`admin` + `cashier`), backed by real-time updates via the `orders` channel from prompt 03. The status-transition action fires stock deduction specifically on the `preparing` transition — this logic lives in the backend (an Order model observer or service), the React page just triggers the transition via a form submission.
- **Inventory** — `Pages/Admin/Inventory/Index.tsx` (`admin` only) showing derived stock with the locked, concurrency-safe deduction logic.
- **Cash payment recording** — a payment dialog/form on the Orders page (`admin` + `cashier`), including partial payments; `payment_status` derived from `SUM(payments.amount)` vs `orders.total`.
- **Kitchen Display** — `Pages/Admin/Kitchen/Index.tsx` (`admin` + `kitchen_staff`), a read-only real-time grid of active orders grouped by type.

## How to work
Use the `plan-council-code-test` skill. Split into one task per page/surface (Menu, Orders/POS, Inventory, Kitchen Display) rather than one giant task. For Orders and Inventory specifically, the council's testing/ops reviewer should explicitly require a backend test that fires two simultaneous deduction attempts against the same ingredient before considering that task done — the concurrency risk here has nothing to do with tenancy and doesn't go away just because multi-tenancy did.
